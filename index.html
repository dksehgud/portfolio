발견·재검증

기존 대기열 수치만으로는 동시 요청의 ‘접수 순서’를 명확히 설명하기 어려웠습니다.

토큰은 사용자를 식별하지만 요청 순서를 나타내지 않고, 시간값은 같은 시각에 들어온 요청의 서버 수신 순서를 구분하기 어렵다고 판단했습니다.

원인·영향

기존 구조에는 동시 요청의 접수 순서를 구분할 고유 순번이 없었습니다. 순번 발급·대기열 저장·상태 저장을 개별 명령으로 처리하면 일부만 반영될 위험도 있었습니다.

선택 이유·적용

INCR로 모든 서버가 공유하는 증가 순번을 만들고, 순위 조회와 이탈 제거가 가능한 Sorted Set에 저장했습니다. 세 명령은 Lua로 묶어 원자 처리했습니다.

02
위험·검증

취소 요청이 없는 연결 종료에서도 서버가 슬롯을 회수할 기준이 필요했습니다.

브라우저 종료 시 취소 요청 전달을 보장할 수 없으므로, Heartbeat가 끊긴 뒤 서버가 슬롯을 회수해 다음 사용자를 입장시키는 시간을 검증 항목으로 정했습니다.

원인·영향

정상 취소는 즉시 처리되지만 연결 종료는 클라이언트의 취소 요청을 보장할 수 없어 서버가 이탈 여부를 판단해야 했습니다.

선택 이유·적용

서버가 마지막 응답 시각을 기준으로 회수하도록 Heartbeat와 connection lease를 두고 scheduler가 만료 슬롯을 정리하게 했습니다.

국가별 삼성닷컴은 DOM과 옵션 구조가 달랐고, 일부 페이지는 HTML과 API 응답을 함께 사용했습니다.

고정된 수집 규칙만으로는 변경 대응이 어려웠고, LLM 생성 코드를 그대로 채택하면 실행에 성공해도 잘못 수집된 값을 놓칠 수 있어 생성과 검증을 분리했습니다.

기술 선택 이유

동적 화면을 실제 브라우저처럼 조작하고 DOM과 네트워크 응답을 함께 확인하기 위해 Playwright를 사용했습니다.

적용

추출 정보를 OpenAI API에 전달해 페이지별 코드를 생성·실행하고, 실행 오류와 비교 결과를 팀원과 공동 구현한 재시도 흐름에 전달했습니다.

개인 구현 범위

브라우저 접근·DOM 추출·API 호출·생성 코드 실행·기준 데이터 비교를 담당했습니다. 오류 재시도와 FastAPI 엔드포인트는 공동 구현했습니다.

검증 범위 생성 코드의 실행 여부와 기준 데이터 비교 절차까지 구현했습니다. 운영 배포와 페이지 변경에 대한 장기 회귀 검증은 후속 과제입니다.
